SECURITY & BUG FIXES LOG
========================================
- [BACKEND / SECURITY] Removed `role` from the public register endpoint's
  Zod schema. It previously accepted an optional `role` field on a route
  anyone can hit unauthenticated, meaning any visitor could self-register
  as Admin or Cashier. New accounts now always fall back to the Mongoose
  schema default ("Customer"). Staff accounts are created through the
  separate Admin-only POST /api/users/staff endpoint (before it existed
  this was done by editing `role` directly in MongoDB Atlas).
- [BACKEND / FEATURE] Order can now reference the Table it came from
  (`table` field, optional). createOrder validates the table exists and
  automatically sets Table.currentOrder + status "Occupied" - staff no
  longer have to link them manually via PUT /api/tables/:id.
- [BACKEND / PERMISSIONS] Cashier can now cancel pending orders. cancelOrder
  only allowed the order's owner or an Admin, so the person running the
  counter couldn't cancel an order without escalating. Cashier is now
  treated as staff there, consistent with isAdminOrCashier everywhere else.
- [BACKEND / BUG] The "new_order" socket event emitted the raw, unpopulated
  document (meals.meal / user / table as bare ObjectIds), so a live-arriving
  order would show blank meal names on the Cashier board until a refetch.
  The order is now populated before emitting, matching getAllOrders' shape.
- [FRONTEND / BUG] authApiSlice was calling /api/auth/* - corrected to
  /api/users/* to match the actual backend route prefix.
- [FRONTEND / BUG] Register form + Zod schema were missing `phone`, which
  the backend requires - every registration failed with a 400 until fixed.
- [FRONTEND / BUG] getProfile returned the backend's raw
  {success, message, user} envelope instead of the User object, so every
  role check in ProtectedRoute silently saw `undefined`. Fixed with
  transformResponse. Same pattern applied proactively to menuApiSlice,
  ordersApiSlice and the other slices to avoid repeating the bug.
- [FRONTEND / BUG] OrderCard crashed ("Cannot read properties of null") on
  an order whose user had been deleted: a populated ref resolves to null
  when its document is gone, and `typeof null === "object"` slipped past
  the string-vs-object check. Order types now model `| null` for
  user / meal / table and the card handles it explicitly.
- [FRONTEND / BUG] File uploads arrived at the server with no file.
  axiosInstance fixes "Content-Type: application/json" as a default, which
  stops the browser from setting the multipart boundary on a FormData body.
  axiosBaseQuery now detects FormData centrally and drops that header, so
  this is fixed for every current and future upload, not just one call.
- [FRONTEND / BUG] MealFormModal type errors ("price: unknown", handleSubmit
  signature) came from z.coerce.number(): its input type is `unknown` while
  the inferred form type said `number`. Replaced with a plain z.number()
  and valueAsNumber on the input's register call.
- [FRONTEND / FIX] MealFormModal used form.watch("image"), which React
  Compiler's lint rule flags as non-memoizable; switched to useWatch
  (same live value, compiler-safe).
- [FRONTEND / UX] Login now returns the user to the page they originally
  tried to reach (location.state.from) instead of a fixed role route;
  added RootRedirect so "/" sends an already-authenticated user straight
  to their role's home page instead of always bouncing to /login.
- [FRONTEND / UX] Toast default position changed from top-right to
  top-center for consistency across the app.
- [FRONTEND / DESIGN] Unified the whole app onto one warm, restaurant-
  appropriate brand palette (brand-cream / brand-charcoal / brand-orange
  / brand-orange-dark / brand-peach, defined once via Tailwind v4 @theme
  in index.css) instead of the generic slate/blue scaffold default.
  Applied across auth pages, protected-route loading states, and the
  menu/cart/checkout flow. Semantic colors (red for errors/403, green
  for success toasts) deliberately left untouched - brand color replaces
  neutral/structural color only, never a status signal.
- [FRONTEND / UX] Menu page overhaul: added a sticky Navbar (brand mark +
  "Dine-in" badge), a welcome banner, a MealDetailModal that opens on
  card click, and a floating CartBar (bottom, rounded, hidden when the
  cart is empty) - replacing the earlier bare grid-of-cards-with-an-
  Add-button version. MealCard's "Add" button was replaced entirely by
  the same +/- stepper used once an item is in the cart, shown from the
  start.
- [FRONTEND / A11Y] All +/- and add-to-cart buttons bumped to 48x48px
  (with leading-none so the glyph sits visually centered, not just
  flex-centered) - the app is used on a phone in a restaurant, not
  clicked on desktop. MealCard is keyboard-operable (role="button",
  tabIndex, Enter/Space, visible focus ring, aria-labels).
  MealDetailModal closes on Escape and locks background scroll while
  open. Broken image URLs fall back to the "No image" placeholder via
  onError, not just missing ones.
- [FRONTEND / FIX] CheckoutPage originally prefilled the phone field from
  the user's profile via useEffect + setState - a pattern React's own
  docs ("You Might Not Need an Effect") and eslint-plugin-react-hooks'
  newer rule both flag as causing an avoidable extra render. Replaced
  with the recommended pattern: adjusting state directly during render,
  guarded by a comparison so it only fires once when the profile value
  actually arrives, not on every render.
- [FRONTEND / FEATURE] Logout. There was no way to end a session. The auth
  cookie is httpOnly (JS can't clear it), so this needed a server endpoint;
  the shared LogoutButton calls it, navigates to /login, then resets the
  whole RTK Query cache so an Admin's orders/revenue don't linger in memory
  for the next person on the same device. Added to the customer Navbar and
  to the Cashier and Admin headers.
- [BACKEND / UX + SECURITY] Sessions ended abruptly: the JWT lived a flat
  1 day from login, so a Cashier who opened the dashboard at the start of
  a shift would start getting 401s on status updates later (the socket
  only checks the token at handshake, so the board still LOOKED alive).
  Replaced with a sliding session: any authenticated request renews the
  cookie once the token is a day old (7-day idle window), capped at 30
  days from the original login via an `authTime` claim carried through
  every renewal. Active users stay in, abandoned sessions still expire,
  and a stolen cookie can't be kept alive forever. The renewal rule lives
  in utils/session.ts and is unit-tested. Deleting/demoting a user still
  takes effect at once because the middleware re-reads the user from the
  DB on every request.
- [BACKEND / FEATURE] First-Admin bootstrap. Public register can't assign
  roles and POST /api/users/staff needs an existing Admin, so the very
  first Admin had no way to exist except a manual DB edit. `npm run
  seed:admin` creates it from ADMIN_* env vars: validated with the same
  Zod schema as the staff endpoint, password hashed through the normal
  save() path, idempotent (no-op if any Admin exists), and it refuses
  rather than silently promoting an email already registered as a
  Customer. Deliberately NOT "first registered user becomes Admin": on a
  freshly deployed public instance that would hand the whole system to
  whoever registers first.
- [BACKEND / SECURITY] "new_order" was broadcast to EVERY connected
  socket (io.emit) with a populated payload: customer name, email, phone
  and delivery address. Harmless while only staff dashboards opened
  sockets, but the moment customers connect for live tracking, any
  customer would receive every other customer's order. It now goes to
  staff_room only.
- [BACKEND / BUG] A customer couldn't read their own order: GET
  /api/orders/:id was Admin/Cashier only, so the tracking page had no way
  to load its initial state. It is now open to the order's owner and
  staff, and the ownership check runs BEFORE populate (while order.user
  is still a bare id). Covered by three new integration tests (own
  order -> 200, someone else's -> 403, staff -> 200).
- [BACKEND / BUG] status_changed was emitted only to the per-order room,
  so the Cashier board never heard about changes it didn't make itself
  (a customer cancelling, another staff member advancing an order). It
  is now sent to the order room AND staff_room via one chained .to(),
  delivered once to anyone in both.
- [FULL-STACK / RELIABILITY] Missed events: Socket.IO doesn't replay what
  a client missed while offline or still connecting, so a wifi blip - or
  an order created between the board's first fetch and its socket
  finishing the handshake - could silently drop an order from the
  Cashier's board. Both live views now re-sync over REST on every
  connect ("subscribe, then sync"); track_order gained an ack so the
  tracking page re-fetches only once its room is actually joined, and
  new_order is de-duplicated against a concurrent re-sync.
- [FRONTEND / REFACTOR] The socket URL derivation and connection setup
  now live in one createSocket() helper (src/api/socket.ts) instead of
  being repeated per hook; order label helpers (type, meal name, short
  id) are shared by the Cashier card and the tracking page.
- [BACKEND / BUG] The payment refactor was only half applied: the types
  and the payments controller already used paymentMethod / paymentStatus /
  paymobOrderId, but the Mongoose schemas and the order validator didn't
  know them. Mongoose silently drops unknown fields, so every
  POST /payments/create would have answered 400 (paymentMethod always
  "undefined") and the webhook could never find its Payment (paymobOrderId
  never saved). Order and Payment schemas + createOrderValidate now carry
  the fields; paymentStatus is deliberately NOT accepted from the client.
- [BACKEND / BUG] Online orders rang the bell before being paid.
  createOrder marked the table Occupied and emitted new_order for every
  order, so an abandoned Paymob checkout left a ghost order on the
  Cashier's board (and the kitchen might cook it). Now createOrder only
  publishes CASH orders; online orders are published by the webhook once
  the payment is confirmed. Both paths share publishOrderToStaff, so
  "what happens when an order goes live" lives in one place.
- [BACKEND / SECURITY] Staff could see and advance an unpaid online order:
  GET /orders listed it and PATCH /:id/status accepted it. List/stats
  queries now exclude online orders that aren't paid, and updateOrder
  refuses them (hiding a card in the UI is not a guard). The filter uses
  `paymentMethod: { $ne: "online" }` so orders created before the field
  existed stay visible.
- [BACKEND / BUG] Tables never became free again: an order completing or
  being cancelled left the table "Occupied" with a stale currentOrder,
  which also made DELETE /api/tables/:id impossible forever. releaseTable()
  now runs on complete / cancel / delete, and only frees the table if its
  currentOrder is still THAT order (a newer order may already own it).
- [BACKEND / BUG] The same meal sent twice in one order (two lines) made
  the "every id was found" check report a meal as missing, and
  isAvailable was never checked, so a switched-off meal could still be
  ordered. Duplicate lines are merged server-side (quantities summed) and
  unavailable meals are rejected with their names.
- [BACKEND / SECURITY] The meal search term went straight into $regex on a
  public endpoint - a crafted pattern could trigger catastrophic
  backtracking (ReDoS). It is now regex-escaped and matched literally.
- [BACKEND / SECURITY] JWT_SECRET had a hardcoded public fallback in every
  environment, so a production deploy that forgot the variable would sign
  sessions with a secret anyone can read in the repo. The server now
  refuses to start in production without it.
- [BACKEND / SECURITY] Added helmet (security headers; CSP off on purpose
  for a JSON API + Swagger UI), `trust proxy` (behind Railway every
  request otherwise shares the proxy's IP) and a rate limit on login +
  register (20 / 15 min / IP, production only so dev and the test suite
  aren't locked out). The README already claimed rate limiting - it is
  real now.
- [BACKEND / SECURITY] test-socket-client.js had a real JWT hardcoded in a
  tracked file. It now reads TEST_TOKEN from .env. ROTATE JWT_SECRET if
  that token was ever valid against production - anything committed must
  be treated as leaked.
- [FRONTEND / BUG] MealsPagination declared `totalPaged` while the backend
  sends `totalPages`, and RegisterInput still allowed a `role` the backend
  rejects. Both types now mirror the real API.
- [FRONTEND / FEATURE] Price reconciliation at checkout. After the order is
  created, the SERVER's total is compared (in piastres, to avoid float
  noise) with the total the customer saw. If they differ, a modal shows
  the new price and the customer must Continue or Cancel the order (the
  cart is kept intact until they decide).
- [FRONTEND / FEATURE] Online payment. Checkout offers Cash or Online;
  online creates the order, calls POST /payments/create and redirects to
  Paymob's hosted checkout (the backend builds the URL, so the frontend
  never touches a Paymob key). If starting the payment fails, the
  customer lands on the tracking page, which offers "Try payment again".
- [FRONTEND / FEATURE] Tracking page handles payment states. Paymob sends
  the customer back BEFORE the webhook usually arrives, so for an unpaid
  online order the page shows "Confirming your payment...", listens for
  payment_status_changed, and polls every 5 s as a safety net (events are
  never replayed). A failed payment shows a retry button. The redirect's
  query params are never trusted - only what the signed webhook recorded.
- [FRONTEND / UX] Cashier cards show a "Paid online" / "Cash" badge so the
  person at the counter knows whether there is money to collect.

========================================
PHASE 2 / FUTURE IDEAS (documented, not built yet)
========================================
- Refund flow (Paymob): a payment that succeeds for an order cancelled in
  the meantime is currently only logged ("needs a manual refund"). Needed
  both for that case and for reservation deposits below
- Refresh-token rotation (short-lived access token + DB-stored, revocable
  refresh token) as the stronger successor to the current sliding
  session, which can't revoke an individual session - only deleting or
  demoting the user takes effect immediately
- Per-line price snapshot on orders (priceAtOrder): an order stores meal
  refs + quantities + one server-calculated totalPrice, so a line's price
  is only knowable from the CURRENT meal price. Customer-facing views
  therefore show names, quantities and the order total only. A snapshot
  would also make historical revenue reports exact if prices change.
- Staff management list (view / deactivate / change role) - creation is
  done, but there is no GET /api/users endpoint or UI to see who has staff
  access
- Analytics date ranges (today / this week / this month): the stats
  endpoint currently aggregates all-time totals
- Takeaway ready-time estimate / "your order is ready" notification so the
  Order Ahead flow tells the customer when to arrive
- Meal discounts / promotions
    - Decision needed: percentage vs fixed amount
    - Likely needs separate "Promotion" collection (with start/end dates)
      rather than a static field on Meal, to support real time-limited offers
- VIP / membership tiers
    - Must be a separate field (e.g. membershipTier) - NOT mixed into
      existing `role` field, which represents system permissions, not
      marketing/loyalty status
- Pagination on Order.find() / heavier list endpoints: the Cashier board
  fetches one page of 100 and splits it by status client-side - fine at
  demo scale, the real bottleneck for a busy restaurant
- Menu/Cart fetch one page of 100 meals to cross-reference prices; a menu
  larger than that would show "unavailable" lines - fix with a by-ids
  endpoint when the menu grows
- Category existence check on Table.currentOrder reference (minor gap)
- Reservation deposits: distinct from a Dine-in order (which assumes the
  customer is already physically at the table) - a true Reservation
  (book a table for a future date/time, before arriving) with a
  refundable deposit to cut down on no-shows: full refund if cancelled
  in time, partial refund if not, forfeited on no-show. Would need: its
  own Reservation entity (date/time, table availability, distinct from
  Table.status="Reserved" which is currently Admin/Cashier-only), a
  Payment tied to the reservation rather than an order, and a partial-
  refund flow through Paymob (see the refund idea above).
  Deliberately not started until the next steps above are done.

========================================
KNOWN ARCHITECTURE DECISIONS WORTH REMEMBERING
========================================
- Auth: httpOnly cookies (not Bearer tokens) - correct choice since this
  is a single web frontend talking to its own backend. Would add hybrid
  Bearer support later if a mobile app or third-party API access is added.
  -> Frontend MUST use withCredentials: true on every request (Axios/RTK
     Query base config) or auth will silently fail via CORS.
  -> Because the cookie is httpOnly, logout has to be a server call that
     clears it; login and logout share one cookie-options constant so
     clearCookie always matches the attributes the cookie was set with.
- All ObjectId string->ObjectId conversions go through a single
  toObjectId() helper (validates + converts, throws 400 on invalid format)
- All Zod validators use .strict() to reject unexpected fields
  (e.g. blocks client-sent totalPrice tampering)
  -> Frontend cart totals are for UI/UX only; the server is the source of
     truth for price calculation and re-validates on every order. The
     checkout reconciles the two and lets the customer decide on a mismatch.
- Global error handler is the single source of truth for error response
  shape - controllers just call next(error)
  -> Frontend's global Error Boundary / Toast system should be built
     around this single response shape.
- assertUser / assertExists helper functions (TypeScript type predicates)
  eliminate repeated null checks across controllers
- Public routes never accept a client-supplied `role`, `totalPrice`,
  `paymentStatus` or any other field that determines trust/money - those
  are always server-derived or Admin-only. Privileged capabilities
  (creating staff) live on separate Admin-only endpoints rather than as
  optional fields on public ones. This is a running principle, not a
  one-off fix (see Security & Bug Fixes Log).
- An order "goes live" at exactly one moment: cash = when created,
  online = when the signed webhook confirms the payment. Both paths call
  publishOrderToStaff (utils/orderEvents.ts); releaseTable is its mirror
  image when the order ends. Until an online order is paid it is invisible
  to staff in lists, stats and the status endpoint (a UI-only hide is not
  a guard).
- Payments: the browser redirect back from Paymob is NEVER trusted. Only
  the HMAC-verified webhook marks anything paid; the webhook finds its
  payment by Paymob's SIGNED order id (never merchant_order_id), checks
  the signed amount/currency, and applies every change as an atomic
  compare-and-set so retries and simultaneous callbacks are harmless.
  Each POST /payments/create is a fresh attempt, so "try again" is just
  calling it again.
- Cart slice stores mealId+quantity references only, never a price/name
  snapshot - same "references over embedding" principle as Meal/Category
  on the backend. Price/name are read live from the meals RTK Query
  cache at display time (useCartLines cross-references cart items
  against a broad, unfiltered meals fetch; useCartSummary reuses it).
  tableId lives inside the cart's own state (not in the localStorage
  key) - switching to a different table silently clears the cart;
  landing on /menu without a table param is a no-op, not a forced
  delivery/takeaway mode.
- Brand color tokens are defined once (index.css @theme) and reused via
  Tailwind utility classes everywhere - never a one-off hex value in a
  component. Semantic colors (error red, success green) are kept
  separate from brand color on purpose.
- Plan.txt line ordering should reflect real dependencies, not just the
  order features were originally imagined in - reorder items when a
  dependency becomes clear instead of leaving a misleading checklist.
- Dine-in (customer already at a table, ordering now) and Reservation
  (booking a table for later, before arriving) are deliberately treated
  as two different concepts, not two states of the same feature - see
  the reservation-deposit Future Idea above.
- React state that mirrors an external/async value (like prefilling a
  form from a profile fetch) is adjusted directly during render with a
  guarded comparison, not via useEffect + setState - avoids an
  unnecessary extra render and matches React's own recommended pattern.
- Real-time dashboards: initial load over REST, then socket events are
  patched directly into the RTK Query cache (updateQueryData) instead of
  polling or refetching. The socket lives only while the dashboard is
  mounted, and the query args are exported from one place so cache
  patches always hit the right cache entry.
- Order board moves are forward-only buttons, not free drag-and-drop,
  because the backend state machine only permits one direction
  (pending -> preparing -> completed; cancelled is terminal).
- Image uploads go to Cloudinary through multer's MEMORY storage and are
  streamed straight on - never written to disk, because Railway's
  filesystem is ephemeral and disk-stored files would vanish on the next
  deploy. The Cloudinary credentials live only in the backend env; the
  frontend never sees a secret, it just receives the resulting URL.
- Express route order matters: static paths (GET /orders/stats) are
  declared before parameterised ones (GET /orders/:id), otherwise the
  param route swallows them.
- Anything that sends FormData goes through the shared axiosBaseQuery,
  which drops the instance's fixed JSON Content-Type for FormData bodies
  so the browser can set the multipart boundary itself.
- Logout resets the entire RTK Query cache (apiSlice.util.resetApiState)
  so one user's cached data (an Admin's orders, revenue) never outlives
  their session on a shared device.
- Session lifetime is a sliding window with a hard ceiling (7-day idle
  window, renewed at most once a day, 30-day absolute cap from the
  original login). The three numbers and the ONLY place that sets the
  auth cookie live together in utils/session.ts, so login, renewal and
  logout can't drift apart. Trade-off: individual sessions can't be
  revoked (only deleting/demoting the user kills them) - a refresh-token
  table would fix that, see Future Ideas.
- The first Admin is bootstrapped out-of-band (seed script), never
  through an HTTP path - any in-app way to mint the first Admin is a way
  for an attacker to do the same.
- Real-time is "subscribe, then sync": events are a freshness
  optimisation, never the source of truth. On every (re)connect the
  client re-fetches over REST (the tracking page after the room-join
  ack), because Socket.IO doesn't replay what was missed while offline.
  The tracking page additionally polls while a payment is unconfirmed.
- Socket rooms are the access-control boundary: order_<id> rooms are
  joined only after an owner/staff check, staff_room holds Admin/Cashier
  sockets, and anything carrying personal data (new_order) is emitted to
  staff_room - never io.emit.
- A customer-facing order view never shows per-line prices (see the
  price-snapshot Future Idea): names, quantities and the order's stored
  total are the only figures guaranteed to be consistent.
- Operational guards belong at the edge of the app: helmet, trust proxy
  (one hop, for Railway) and a production-only rate limit on the public
  auth routes; the server refuses to boot in production without
  JWT_SECRET. Secrets never live in tracked files (test-socket-client.js
  reads TEST_TOKEN from .env).
